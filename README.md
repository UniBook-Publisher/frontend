# UniBook Publisher: frontend

SPA веб-клієнт платформи UniBook Publisher, побудований на базі React 19, TypeScript та Vite. Клієнт забезпечує графічний інтерфейс для супроводу повного життєвого циклу рукописів: подання автором, редактура, версіонування правок, дизайн обкладинок, підтвердження фінансових контрактів та сповіщення.

## 2. Архітектурний підхід (FSD)

Проєкт дотримується методології Feature-Sliced Design, що забезпечує високу масштабованість, модульність та легку підтримку коду.

### 2.1. Опис шарів

Код розміщено у паці `src/` і розділено на суворі шари відповідно до їхньої відповідальності:

- `app/` — Точка входу в застосунок. Містить глобальні провайдери (`QueryClientProvider`, `AuthProvider`), конфігурацію роутера (`router.tsx`), глобальні стилі та ініціалізаційну логіку (`App.tsx`).
- `pages/` — Композиційний шар сторінок (`LoginPage`, `RegisterPage`, `ManuscriptsPage` тощо). Сторінки збирають разом бізнес-фічі та віджети, але самі не містять складної бізнес-логіки.
- `features/` — Ізольовані бізнес-функціональності користувача (наприклад, `auth`, `manuscripts`, `contracts`, `notifications`). Кожна фіча містить власну внутрішню структуру:
  - `api/` — React Query мутації та хуки запитів (`useLoginMutation`, `useRegisterMutation`).
  - `components/` — UI-компоненти, специфічні для цієї фічі (наприклад, `LoginForm`).
  - `model/` — Стейт-менеджмент, контексти сесії (`useSession`) або локальні схеми валідації.
  - `index.ts` — Публічний API фічі.
- `shared/` — Перевикористовуваний код, що не прив'язаний до конкретної бізнес-домену:
  - `api/` — Інстанс `apiClient`, обробка RFC 9457 `ProblemDetail`, автозгенерований `schema.d.ts`.
  - `ui/` — Базові UI-компоненти (дизайн-система на основі Radix UI / Shadcn: `Button`, `Input` тощо).
  - `lib/` — Допоміжні утиліти (нотифікатори помилок `notifyApiError`, мапери форм `applyApiErrorToForm`).
  - `config/` — Глобальні конфігурації та змінні оточення.
  - `types/` — Загальні TypeScript-типи.

### 2.2. Правило однонаправленого потоку залежностей

Залежності імпортуються виключно зверху вниз:

**app** → **pages** → **features** → **shared**

Модуль із нижчого шару ніколи не може імпортувати код із вищого шару (наприклад, `shared` не може імпортувати з `features`). Кожна фіча або компонент взаємодіє з іншими лише через публічний інтерфейс — `index.ts`. Дотримання цих правил гарантується плагіном `eslint-plugin-import-x`.

## 3. Ключові технічні рішення

### 3.1. Типізація API без кодогенерації методів

Замість важких генераторів REST-клієнтів використовується легка зв'язка openapi-fetch та openapi-typescript:

1. На основі OpenAPI v3 специфікації бекенду команда `pnpm api:generate` автоматично оновлює файл `src/shared/api/schema.d.ts`
2. `apiClient` підхоплює згенеровані TS-типи schema. Всі HTTP-запити (`POST`, `GET`, `PUT`, `DELETE`), їхні Query/Path параметри та Request/Response Body мають 100% автодоповнення та строгу перевірку типів на етапі компіляції.

### 3.2. Керування станом та кешуванням (TanStack Query v5)

ля збереження асинхронного стану бекенду використовується TanStack Query v5:

- Глобальна обробка помилок (Global Error Interceptors): У `QueryCache` та `MutationCache` перехоплюються мережеві помилки. Помилки RFC 9457 (`ApiError`) автоматично транслюються у пласкі тости через бібліотеку `Sonner`.
- Пригнічення тостів (`silent: true`): За допомогою TypeScript Module Augmentation розширено глобальний інтерфейс `Register`:

```typescript
declare module '@tanstack/react-query' {
  interface Register {
    queryMeta: { silent?: boolean };
    mutationMeta: { silent?: boolean };
  }
}
```

Це дозволяє передавати `meta: { silent: true }` у локальних формах (наприклад, при логіні/реєстрації), де помилки виводяться безпосередньо під інпутами без створення спаму глобальних тостів.

### 3.3. Безпека авторизації

Система реалізує безпечну гібридну модель авторизації:

- **Access Token**: Передається у відповіді API і зберігається у пам'яті фронтенду. Автоматично підставляється у заголовок `Authorization: Bearer <token>` під час кожного запиту.
- **Refresh Token**: Зберігається у захищених httpOnly cookie з обмеженим шляхом (`path=/api/v1/auth`, `SameSite=Lax`). Браузер самостійно надсилає куку при виклику `/refresh` та `/logout`, що повністю захищає токен від XSS-атак.
- **Single-Flight Refresh**: Якщо під час виконання запиту Access Token виявляється протермінованим (HTTP 401), HTTP-клієнт ставить поточні запити на паузу, проводить одиночне оновлення пари токенів через `/api/v1/auth/refresh` та прозоро повторює вихідні запити.

```
frontend/
├── .husky/                   # Git hooks (pre-commit перевірки)
├── public/                   # Статичні файли
├── src/
│   ├── app/                  # Точка входу, роутер, провайдери
│   │   ├── providers/        # QueryProvider, AuthProvider
│   │   ├── App.tsx           # Кореневий компонент

│   ├── features/             # Ізольовані бізнес-фічі
│   │   └── auth/             # Фіча автентифікації
│   │       ├── api/          # useLoginMutation, useRegisterMutation, useLogoutMutation
│   │       ├── components/   # Компоненти форм авторизації
│   │       ├── model/        # useSession, AuthContext
│   │       └── index.ts      # Публічний API фічі auth
│   ├── pages/                # Сторінки додатка (LoginPage, RegisterPage, ...)
│   └── shared/               # Перевикористовувані ресурси
│       ├── api/              # apiClient, schema.d.ts, problem-detail
│       ├── config/           # Змінні оточення та константи
│       ├── lib/              # Утиліти (notify-error, form-error)
│       ├── types/            # Спільні TS-типи
│       ├── ui/               # Базові UI компоненти (Button, Input, Card, ...)
│       ├── index.css         # Tailwind CSS v4 імпорти
│       └── main.tsx          # Рендер у DOM
├── .env.example              # Шаблон змінних середовища
├── eslint.config.js          # Конфігурація ESLint 10 (Flat Config)
├── package.json              # Залежності та скрипти
├── tsconfig.json             # Налаштування TypeScript (Strict Mode)
└── vite.config.ts            # Конфігурація Vite 8
```

## 5. Налаштування та запуск

### 5.1. Вимоги

- **Node.js**: `^24.0.0` (версія зафіксована у `.nvmrc`)
- **pnpm**: `>=10.0.0` (зафіксовано у `packageManager`)

### 5.2. Інсталяція та локальний запуск

1. Клонувати репозиторій та встановити залежності:

```bash
git clone https://github.com/UniBook-Publisher/frontend.git
cd frontend
pnpm install
```

2. Підготувати змінні середовища:

```bash
cp .env.example .env
```

3. Запустити Dev-сервер:

```bash
pnpm dev
```

Додаток буде доступний за адресою http://localhost:3000. Усі запити на `/api` автоматично проксуються на бекенд http://localhost:8080 завдяки конфігурації Vite proxy.

## 7. Контроль якості та Git Hooks

У проєкті налаштовано багаторівневу систему контролю якості:

- **ESLint 10 (Flat Config)** перевіряє дотримання React Hooks, A11y (доступність), правильність імпортів та правила архітектурних меж FSD.
- **Husky + lint-staged**: При виконанні `git commit` автоматично запускаються перевірки `eslint --fix` та `prettier --write` виключно для змінених файлів (staged files). Запушити недотриманий код у репозиторій неможливо.
- Автоматизований CI-пайплайн на базі GitHub Actions виконує суворий лінтинг, перевірку типів і збірку проєкту, а також проводить автоматичний аналіз вразливостей та якості коду через SonarCloud при кожному push чи Pull Request.
